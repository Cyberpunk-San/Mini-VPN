PART 2: OPERATING SYSTEMS (OS) CONCEPTS (Speak clearly here)
================================================================================

When the teacher asks: "How does this relate to Operating Systems?"

Say:
"Professor, this project is built directly on fundamental OS kernel primitives:

1. Virtual Network Devices (TUN / ioctl):
   Standard applications read and write to physical network cards. MiniVPN uses 
   the Linux kernel's '/dev/net/tun' character device. Using ioctl system calls 
   with 'TUNSETIFF', our C program allocates a virtual network interface in 
   software. When a user application generates an IP packet, the OS kernel routes 
   it directly into our program's file descriptor instead of a physical wire.

2. Event-Driven I/O Multiplexing (epoll, signalfd, timerfd):
   Instead of the traditional 'thread-per-connection' model—which wastes kernel 
   memory and causes excessive context-switching overhead—MiniVPN is entirely 
   single-threaded and non-blocking. We use the Linux 'epoll' system call. 
   Furthermore, we use 'signalfd' to handle Unix signals and 'timerfd' to handle 
   retransmissions and timeouts as standard file descriptors. Everything is 
   unified into a single epoll event loop, allowing sub-millisecond packet 
   processing.

3. Privilege Separation & Dropping (setuid / setgid):
   To follow the Principle of Least Privilege: MiniVPN starts execution as 
   root strictly to acquire kernel network capabilities and configure the TUN 
   device. Immediately after initialization, it drops its privileges using the 
   'setuid' and 'setgid' system calls to an unprivileged system user ('minivpn'). 
   Even if an attacker were to exploit a buffer vulnerability in memory, they 
   would be trapped in an unprivileged sandbox without root access.

4. Inter-Process Communication (IPC) with Peer Credential Verification:
   The Python web dashboard communicates with the running C daemon through a 
   Unix domain socket ('/run/minivpn/control.sock'). To prevent unauthorized local 
   users from controlling the VPN, our C server inspects the 'SO_PEERCRED' socket 
   option at the kernel level to verify the UID and GID of the connecting process 
   before executing commands."

PART 3: COMPUTER NETWORKS (CN) CONCEPTS (Speak clearly here)
================================================================================

When the teacher asks: "How does this relate to Computer Networks?"

Say:
"Professor, MiniVPN implements a full networking protocol stack:

1. IP-in-UDP Encapsulation:
   MiniVPN is a Layer 3 (Network Layer) VPN. It intercepts raw IPv4 packets from 
   the virtual TUN interface, encapsulates them inside standard UDP datagrams on 
   port 51900, and sends them across the underlying Internet.

2. Modern Cryptographic Architecture:
   We do not use deprecated or slow ciphers. We implemented modern primitives:
   - Key Exchange: X25519 Elliptic Curve Diffie-Hellman (ECDH) for Ephemeral-
     Static key agreement, providing Perfect Forward Secrecy.
   - Key Derivation: HKDF-SHA256 (RFC 5869) to derive symmetric session keys.
   - Authenticated Encryption: ChaCha20-Poly1305 AEAD (RFC 8439). Every packet 
     carries a 16-byte cryptographic Poly1305 authentication tag.

3. Anti-Replay Protection:
   UDP is connectionless and prone to packet replay attacks. MiniVPN implements 
   a 64-packet bitmap sliding replay window. If an eavesdropper captures an 
   encrypted packet on the wire and attempts to replay it later, the sequence 
   number check identifies the duplicate and drops it immediately.

4. Routing & Anti-Spoofing:
   The server enforces strict cryptographic binding between each device's X25519 
   public identity and its allocated private IP (e.g. 10.8.0.2). If a compromised 
   client attempts to forge an IP header and impersonate another client, the 
   server detects the mismatch and silently drops the packet."

PART 5: TOUGH QUESTIONS YOUR TEACHER MIGHT ASK (Cheat Sheet)
================================================================================

Q1: "Why did you use ChaCha20-Poly1305 instead of AES-GCM?"
A1: "AES is fast only on processors that have hardware AES-NI instructions. On 
    mobile devices, ARM processors, and older hardware, software AES is slow and 
    vulnerable to cache-timing attacks. ChaCha20 uses simple ARX operations 
    (Add-Rotate-Xor) which execute in constant time on all CPU architectures, 
    making it faster and inherently immune to timing side-channel attacks."

Q2: "What is the difference between a TUN device and a TAP device?"
A2: "A TAP device operates at Layer 2 (Data Link layer) and processes Ethernet 
    frames, including MAC addresses. A TUN device operates at Layer 3 (Network 
    layer) and processes pure IP packets. Because MiniVPN routes IP traffic 
    between devices, using TUN eliminates 14 bytes of Ethernet header overhead 
    per packet, saving bandwidth and simplifying kernel routing."

Q3: "What happens if an attacker modifies 1 bit of the packet on the wire?"
A3: "Because we use Authenticated Encryption with Associated Data (AEAD), each 
    packet has a 16-byte Poly1305 MAC tag calculated over the ciphertext. If an 
    attacker flips even a single bit in transit, the receiver's MAC computation 
    fails, and the packet is immediately discarded before any decryption or 
    processing occurs."

Q4: "Why UDP instead of TCP for the VPN tunnel?"
A4: "If you run TCP-over-TCP (encapsulating TCP traffic inside a TCP VPN tunnel), 
    any packet loss causes both the inner and outer TCP stacks to trigger 
    retransmissions and congestion control back-off simultaneously. This is 
    known as the 'TCP Meltdown Problem'. Running the VPN tunnel over UDP avoids 
    this conflict, allowing the client's native TCP connection to handle its own 
    congestion and retransmission cleanly."
